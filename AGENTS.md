# Контекст спринта NormDoc2JSON

Рабочее ТЗ спринта — «ТЗ для IT.docx», ИНГРО.ТЗ.02-2026, редакция 1.0. Спринт длится семь календарных дней, в нём участвуют два программиста. Таблица 2 задаёт план работ, Приложение А — контракт выходного JSON. «ТЗХЗ.md» (Master Specification v2.0) описывает общую архитектуру проекта «Ингро». Его план модернизации CAD-плагинов, `PartPassport`, расчётного ядра и DFM находится за пределами спринта.

## Что разрабатываем

NormDoc2JSON — консольная утилита и импортируемая Python-библиотека для конвертации нормировочных документов ЦБНТ/ОУНВ в JSON. На вход подаются офисные и табличные документы, PDF с текстовым слоем, сканированные и гибридные PDF, многостраничные TIFF и растровые изображения. На выходе — валидируемые нормировочные карты для расчётного ядра «Ингро».

1. **Маршрутизация.** Определить тип файла, кодировку текстовых форматов, наличие текстового слоя PDF и доступные сведения о DPI изображений.
2. **Извлечение и OCR.** Получить блоки текста и сетки ячеек с координатами. Для сканов и фото нужны выравнивание, очистка изображения и распознавание.
3. **Семантический разбор.** Извлечь заголовок, условия применимости, формулу, оси таблицы, числовую матрицу и поправочные коэффициенты из примечаний.
4. **Валидация и экспорт.** Проверить данные через Pydantic v2 и сохранить JSON в UTF-8 без BOM. Корневые поля — `schema_version`, `source_metadata`, `cards`. Проверить соответствие `values_matrix` осям `rows_range` и `cols_range`, нормализовать десятичную запятую, сохранять пустые ячейки как `null` и диапазоны как `[min, max]`. Ошибки отдельных страниц и сомнительные результаты отражать в журнале и помечать через `requires_manual_review`.

Python 3.10+, целевые системы — Windows 10/11 и Linux (Ubuntu 22.04+). CLI должна поддерживать `--input`, `--output`, `--ocr-lang`, `--strict` и `--debug-images`. К сдаче нужны зафиксированные зависимости, инструкция по системным зависимостям, скрипт инициализации весов OCR для автономной работы, README, спецификация JSON и сгенерированная JSON Schema.

## Ветки и роли

- `main` — основная ветка. Не добавляем в неё коммиты и не сливаем в неё ветки спринта.
- `dev` — ветка разработки и интеграции.
- `day1` … `day7` — ветки задач дня от `dev`. Ветку очередного дня создаём от актуальной `dev`.
- Ветки программистов создаём от ветки дня. Для первого дня — `programmer1` и `programmer2` от `day1`. Изменения идут из веток программистов в ветку дня, затем в `dev`.
- Наша роль — программист 1: извлечение данных и OCR. Программист 2 отвечает за семантику, схему JSON и CLI, а на второй день также за извлечение из текстовых офисных форматов.

## Цели по дням

1. Подготовить каркас проекта, тестовые файлы, маршрутизатор форматов, схему JSON и CLI.
2. Извлекать таблицы и примечания из офисных документов и электронных таблиц.
3. Преобразовывать таблицы из PDF с текстовым слоем в `table_grid`.
4. Подготовить сканы и фото к OCR, научиться извлекать формулы и условия применимости карт.
5. Распознавать таблицы в сканах и фото, извлекать поправочные коэффициенты из примечаний.
6. Собрать и отладить полный конвейер с отметками для ручной проверки.
7. Прогнать контрольный набор, измерить точность, завершить документацию и показать результат.

## Приёмка

- Контрольный набор — минимум 10 файлов. Два векторных PDF, два документа Word, две книги Excel, один сканированный PDF, один многостраничный TIFF, одна фотография страницы и один скриншот таблицы.
- Все выходные JSON проходят валидацию. Точность числовых ячеек — от 98% для структурированных источников и от 85% для сканов и фотографий. Сомнительные ячейки помечаются в журнале и JSON.
- Целевое время — до 1,5 с на страницу структурированного документа и до 8 с на страницу с OCR на CPU. Поддерживаются документы до 200 страниц.
- Расчётное ядро импортирует сгенерированный JSON и использует его для расчёта нормы времени по тестовому валу. Существующие потребители карт находятся в `database/loader.py` и `calc_engine/cbnt_auto_filter.py`. Интеграционная проверка должна подтвердить совместимость с контрактом Приложения А.
